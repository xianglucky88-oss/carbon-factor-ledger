# 因子账本与可追溯重算设计说明

## 1. 领域模型与统一词汇

所有写入都通过**只追加的事件日志**进入账本，事件类型共五种：

| 事件 | 含义 | 不可变性 |
| --- | --- | --- |
| `evidence_registered` | 登记证据文件（文件名 + SHA-256） | 证据身份不可变；同身份不同哈希记为哈希冲突 |
| `factor_version_registered` | 登记因子的某个**版本** | 因子值、单位、地理范围、边界、有效期、证据引用全部冻结在版本内 |
| `factor_withdrawn` | 撤回某个因子版本 | 只置状态位，不删除、不改写版本行 |
| `consumption_recorded` | 产品/期间的一条物料或活动消耗 | 记录不可变；可钉选 `factor_version`，缺省按日期解析 |
| `report_frozen` | 冻结一份产品/期间报告 | 快照复制，后续事件只能标 `superseded`，不能覆盖 |

统一维度由 `units.py` 集中管理：质量（kg/g/t/lb）、能量（kWh/MWh/GJ/MJ）、
距离（km/m/mi）、货运质量距离（tkm/kgkm）、体积与面积；排放单位统一折算为
kgCO2e（kgCO2e/gCO2e/tCO2e）。跨维度换算（如 kWh→kg）抛 `UnitError`，
对应记录隔离为 `UNIT_INCOMPATIBLE`，而不是静默按零处理。

## 2. 适用性判定与隔离原因

每条消耗记录经过完整规则集（`applicability.py`），规则之间**不短路**，
可同时返回多个原因。结果二选一：付费贡献 `Contribution`（含换算后数量、
排放量、证据 id 与证据哈希）或隔离条目 `QuarantineEntry`（带全部原因与明细）。

| 隔离原因 | 触发条件 |
| --- | --- |
| `FACTOR_NOT_FOUND` | 因子未注册，或钉选版本不存在 |
| `EVIDENCE_MISSING` | 因子引用的证据未登记 |
| `EVIDENCE_HASH_MISMATCH` | 同一证据身份再次导入时哈希变化 |
| `FACTOR_WITHDRAWN` | 解析到的版本已被撤回 |
| `FACTOR_EXPIRED` / `FACTOR_NOT_YET_VALID` | 记录日期落在版本有效期外 |
| `GEOGRAPHY_OUT_OF_SCOPE` | 因子地理范围既不等于记录范围也不是 `GLOBAL` |
| `BOUNDARY_MISMATCH` | 生命周期边界不同，或活动/物料流身份不一致 |
| `UNIT_INCOMPATIBLE` | 单位维度不同，无法换算到因子基准单位 |

关键区分：因子**存在但没有任何版本覆盖记录日期** → 过期/未生效；
因子**根本不存在** → `FACTOR_NOT_FOUND`。已撤回版本仍可被解析到，
以便撤回、证据链、地理、边界规则继续叠加判定。

## 3. 证据链与守恒

* 每个 `Contribution` 都携带 `evidence_id` 与计算时刻的 `evidence_sha256`；
  报告输出时该哈希必须等于账本中该证据的登记哈希（测试
  `test_evidence_references_are_closed_and_hash_consistent` 强制校验）。
* 同一证据重复导入且哈希相同 → 幂等无操作，导入计数不增加、状态哈希不变。
* 同一证据以不同哈希再次导入 → 保留原始登记哈希，记录冲突哈希集合，
  所有经该证据背书的因子的下游记录全部隔离为 `EVIDENCE_HASH_MISMATCH`。
* **记录守恒**：每条输入记录恰好出现在贡献或隔离之一，不重复、不丢失、
  不静默归零（隔离记录保留数量与原因）。
* **足迹守恒**：单元足迹 = 其贡献排放量逐笔之和；总足迹 = 各单元之和，
  没有隐藏的舍入桶。
* **证据引用守恒**：单元的 `evidence_refs` 恰好是其贡献证据的去重集合。
* **冻结守恒**：冻结报告复制当时的贡献、隔离、状态哈希；之后的替换、
  撤回、哈希漂移只能把报告标记为 `superseded` 并记录触发事件，快照值永不变。

## 4. 三种重算实现的比较

三者共用同一个账本与同一份逐记录计算代码（`applicability.evaluate_record`
+ `engine.evaluate_cell`），因此**数值必然一致**，差异只在“重算多少”。

### A. 按产品物化（`materialized.py`）

预计算并缓存每个 (产品, 期间) 单元。事件到达时先路由出脏单元集合，
只重算脏单元，其余缓存不动。

* 优点：读取 O(1)；重算范围 = 脏单元数；实现简单、临时状态只有一个单元。
* 缺点：缓存与账本必须同生命周期维护；因子侧事件需要反查受影响单元；
  单元内部无法区分单条记录的精确变化量。
* 适用：产品/期间数量稳定、读多写少的常规结算。

### B. 因子依赖图增量传播（`graph.py`）

节点 = 证据 / 因子（按 factor_id 聚合版本）/ 消耗记录 / 单元汇聚点；
边 = 记录→因子→证据。变更事件从源头沿边反向传播
（证据→因子→记录→单元），只重算可达记录，并按**逐记录排放增量**
调整单元聚合，不做整单元或全账本重建。

* 优点：重算范围最精确（受影响记录数与单元数）；天然回答“某因子撤回
  影响哪些对象”；无需全状态临时副本。
* 缺点：需要维护边索引与节点分类状态；图视图在事务回滚后需重建。
* 适用：因子/证据更新频繁、需要传播解释与影响面分析的供应链场景。

### C. 报告时重算（`engine.full_recompute`）

不维护任何派生状态，读取时从当前账本完整重算全部单元。

* 优点：无缓存一致性问题、实现最直接、永远以当前规则口径出数；
  状态面最小。
* 缺点：每次成本 = 全账本（全部单元、全部记录、全部因子版本）；
  大数据量下昂贵。
* 适用：低频冻结、审计重跑、作为 A/B 的正确性基线。

### 实测行为（测试 `test_incremental_batches_converge_across_strategies`）

多批次（基础数据 → 撤回 → 证据漂移 → 新增记录）下三种策略的总足迹与
账本状态哈希完全相同；首批之后 A/B 的 `cells_evaluated` 始终
≤ C，C 每次都扫描全部单元。

## 5. 重算范围与临时状态的限制

* `RecomputeStats` 显式输出：应用事件数、重算单元数、触达记录数、
  触达因子版本数、受影响产品/期间/报告，使“重算范围”可审计。
* 幂等重放（相同内容哈希事件）在进入策略前被过滤，统计为零触达、零重算。
* 事务边界：`Ledger.apply_batch` 先深拷贝快照，任一事件失败即整体回滚，
  失败不会留下半应用的临时状态；状态化策略在回滚后从账本重建视图。
* 冻结报告不参与实时重算覆盖，只通过 `mark_affected_reports` 标记，
  且仅当触发事件晚于冻结时间、并触及报告单元内记录时才标记。

## 6. 乱序、重复与恢复

* 解析器对事件做**确定性拓扑排序**（实体依赖 + 事件 id 平局判定）：
  证据先于因子、因子先于撤回/记录、冻结事件排在最后；同一批输入任意
  洗牌都产生相同的账本状态哈希。
* 事件 id 缺省由事件内容的规范 JSON 做 SHA-256 生成，天然内容寻址；
  同版本重复执行是幂等无操作。
* 同 id/version 的因子重复登记：内容相同→无操作；内容冲突→拒绝并提示
  改用新版本，杜绝就地覆盖。
* 失败恢复：事件日志是唯一事实来源，把日志重放进新账本即可得到相同的
  状态哈希与足迹（`test_rebuild_from_event_log_recovers_identical_state`）。

## 7. 组合案例覆盖（`fixtures/input.json`）

单份乱序事件流同时覆盖：t→kg 与 kgkm→tkm 单位换算、因子有效期跨越的
版本替换、撤回传播、地理范围不匹配、边界不匹配、证据缺失、未知因子、
跨维度单位、证据哈希漂移、部分产品缺料，以及一份冻结报告。
当前 fixture 的隔离原因计数覆盖全部七种原因；测试
`tests/test_conservation.py` 对足迹、贡献、隔离、证据引用与冻结快照
逐项断言守恒。
